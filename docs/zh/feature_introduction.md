# 特性介绍

本文介绍 gd-hnsw（全局分布式 HNSW 检索算法）的核心特性、设计动机与适用场景。

## 1. 背景与动机

向量检索的目标是：给定查询向量，从数据库中找到与其最接近的 k 个向量。基于图的 HNSW 方法将每个数据向量表示为图节点并建立邻居连接，查询从入口节点出发沿边探索，只需访问部分数据即可获得高质量近邻结果。

数据规模增大后，常见做法是**分片**：各节点在自己的数据分片上独立建图、独立检索，再由协调节点汇聚重排序。该方案存在两个固有缺陷：

- **独立局部图放大总计算量。** 每个查询都要在各分片分别导航。图搜索工作量随数据规模次线性增长，分片变小并不能抵消多次独立搜索带来的额外计算。设数据集含 N 个向量、均匀分布在 P 个分片，基线方案的集群总距离计算量规模约为 `P·log(N/P)`，而一张完整全局图只需 `log N`。
- **每次查询占用所有分片，扩展收益受限。** 即使全局近邻只集中在少数分片，其他分片也要完成本地检索，查询延迟受最慢分片影响。

gd-hnsw 采用**全局图**方案，利用鲲鹏超节点 URMA（用户态远程内存访问）高带宽、低时延的特性，实现分布式全局检索：在全部数据上构建一张完整 HNSW 图，再分片存储到各节点；查询沿同一张全局图跨分片搜索，只生成一份结果。

## 2. 核心特性

### 2.1 全局图索引：跨分片连接

| 对比项 | 分片基线方案 | gd-hnsw 全局检索 |
| --- | --- | --- |
| 索引组织 | 先划分数据，各分片独立建局部图 | 在全部数据上构图，再分片存储 |
| 图的连接范围 | 只连接本分片内的向量 | 保留跨分片边，逻辑上仍是一张完整图 |
| 一次查询 | 各局部图分别搜索再汇聚 | 沿全局图跨分片搜索，生成一份结果 |

分片边界只决定数据在哪里，不限制图搜索的范围。相同召回目标下，全局图减少了各局部图分别导航带来的额外距离计算。

### 2.2 距离下推（Pushdown）

远端邻居的距离有两种取得方式，可按分组混合使用：

- **向量拉取（Pull）**：通过 URMA READ 将远端向量拉回查询节点，本地计算距离；
- **距离下推（Pushdown）**：将计算任务发送到向量所在节点，就地读取本地向量计算，只回传 ID 与距离。

以 10 亿条 1024 维 float32 向量、2 节点均分、单节点 1000 QPS、每查询评价 1 万条向量估算：朴素拉取方案每查询需跨节点传输约 0.02048 GB（有效带宽需求 20.48 GB/s）；距离下推将向量传输替换为"查询向量一次发送 + ID/距离回传"，每查询跨节点传输降至约 64 KB，带宽需求降低两个数量级以上，同时把一半距离计算分担给对端节点。

距离策略支持 `pull` / `pushdown` / `auto`：auto 模式下按分片分组内 ID 数量自动选择（小于阈值拉取，否则下推）。当查询结果集合已满时，下推请求还会携带当前最差结果距离作为上界，远端只回传优于上界的候选，进一步减少响应数据量。

### 2.3 分层数据组织与直接寻址

- **上层图邻接关系**：每个节点保存一份完整副本，导航阶段全部本地访问；
- **底层图邻接表 + 原始向量**：按全局 ID 连续分片存储，与对应图节点同分片放置；
- 通过分片映射 ShardMap 将全局 ID 转换为"所属分片 + 分片内编号"，结合定长布局直接计算数据在本地或远端内存中的位置，**无需先询问对端**。

### 2.4 多线程并行与查询间重叠

每个节点运行相同程序，内部按职责划分线程：查询管理（接入、超时、回收）、搜索执行（维护查询状态、推进搜索）、距离计算服务（处理他节点下推请求）、读取通信（URMA READ 推进）、请求与结果通信（距离请求收发）。单个查询的搜索状态始终由一个搜索线程维护；查询等待远端操作时，搜索线程可切换处理其他就绪查询，实现搜索、通信与距离服务的并行重叠。线程数量支持自动推导与显式配置。

### 2.5 单进程一体化接入

检索能力以库形式嵌入宿主进程，每个进程完成"初始化 → 加载分片 → 节点同步 → 检索 → 释放"的完整生命周期，无全局状态，便于嵌入各类服务进程。接入 Milvus 时，QueryNode 经 CGO 桥直达算法运行时，不经过原生 segcore / knowhere 检索链。接口详情见 [API 参考](api_reference.md)。

## 3. 性能规格

在鲲鹏超节点 4 节点电组网环境（openEuler 24.03 SP3，GCC 12.3，KP950）下，设计目标为：

- 对比 32 分片独立索引方案，同等算力下集群吞吐 QPS 提升 100%；
- 查询时延小于 50 ms；
- 召回率大于 0.95（gist、bge 数据集验收）。

## 4. 适用场景与约束

**适用**：互联网搜推广等超大规模向量检索场景，节点间具备 URMA/ubs-mem 高速互连环境。

**约束**：

- 部署进程（rank）数必须与索引分片数一致（每进程加载一个分片）；
- 依赖 URMA 用户态远程内存访问能力；无 URMA 环境时可单机单分片运行（快速路径，无跨节点通信）；
- 全局索引相比分片索引的构建成本更高，索引构建为离线流程。
