# 特性介绍

本文档介绍gd_hnsw（代码命名空间`hnsw_urma`）的系统架构、核心算法原理与关键特性，帮助开发者理解其工作机理并正确使用。

## 概述

gd_hnsw是一套支持全局分布式向量检索的算法库。它采用HNSW（Hierarchical Navigable Small World，分层可导航小世界）图索引，并通过URMA（Unified Remote Memory Access，统一远端内存访问）实现跨节点数据访问。多个进程共同持有一张覆盖全部数据的HNSW全局图（按分片存储）。任一进程可发起查询：沿图遍历时通过URMA READ直接读取远端进程的图结构与向量，并可将距离计算下推（pushdown）到数据所在进程就近执行。核心以C++20实现，跨节点通信基于UMDK（Unified Memory Development Kit，统一内存开发工具包）/URMA，以独立库形式交付，宿主（如Milvus）经C ABI集成。

## 架构介绍

以下从分层结构、功能模块、部署模型和线程模型四方面介绍当前架构。

### 分层结构

- **接入层**：`ub_c_api.h`以纯C ABI（Application Binary Interface，应用二进制接口）暴露运行时能力（配置、装载、资源发布/导入、启用、检索、释放），供Milvus等宿主集成。
- **运行时层**（`runtime/`）：五类线程的编排与调度（config/thread_group/scheduler/topology），以及距离下推（hybrid_distance）、负载均衡（load_balancing）、优雅退出（drain）、RPC运行时（rpc）。
- **搜索层**（`search/`）：查询任务的搜索状态机、查询池、本地/远端I/O路径（query_context/query_slot_pool/local_io/remote_io/read_resources）。
- **传输层**（`transport/`）：URMA READ/WRITE_NOTIFY的封装与批处理（urma_transport/read_batch_lane/urma_resources），以及节点内共享内存传输（shared_memory_transport）。
- **核心层**（`core/`）：分片映射、访问表、双堆、无锁环、页对齐缓冲区、统一`Status`/`Result`返回。
- **索引层**（`index/`）：索引文件格式（format V2）与参考构建接口；生产环境大规模构建由宿主侧构建组件承担。
- **计算层**（`compute/`）：数据集抽象与距离计算。
- **协议层**（`protocol/`）：距离任务的线格式编解码（distance_batch_wire）。

底层依赖为UMDK/URMA（跨节点数据面）与fmt（日志）。

### 功能模块

**表 1** gd_hnsw功能模块

| 模块 | 功能描述 |
|----------|----------|
| 接入接口（ub_c_api.h） | 对外C ABI：注入上下文、配置、装载、资源发布/导入、启用、检索、释放全生命周期 |
| 分片映射（ShardMap） | 把全局节点ID转换为“所属分片+分片内编号”，支撑数据直接寻址 |
| 上层图副本（UpperGraphReplica） | 每个进程物化一份完整上层图邻接关系，本地读取任意上层节点邻居 |
| 本分片数据（LocalShard） | 第0层邻接表与原始向量，含向量范数缓存与预取 |
| 搜索任务（HnswSearchTask） | 有状态搜索：维护结果集合、候选集与已展开集合，逐轮“取邻接表→算距离→更新集合” |
| 查询池（QuerySlotPool） | 固定数量的查询位置，控制并发查询占用 |
| 距离下推（HybridDistanceOracle） | 将远端邻居的距离计算下发到数据所在进程就近执行 |
| 调度器（Scheduler） | 查询接纳与分配：准入队列、就绪通知、重试与超时管理 |
| 距离线程（Distance） | 处理其他进程下推的距离请求，使用本地向量计算指定ID的距离 |
| 通信线程（READ/RPC Progress） | 推进远端邻接表/向量的URMA READ，收发RPC（Remote Procedure Call，远程过程调用）距离请求与结果 |
| 距离邮箱（RpcMailbox） | requests/responses/notify三段注册内存（对应资源角色2/3/4），与图、向量两块（角色0/1）合为本分片对外发布的五类注册内存；承载距离任务、结果与完成通知 |
| 索引文件（index format V2） | 4KB定长头+数据块，含校验；三类文件组成“三元组” |

上述五类注册内存按对外发布的资源角色计数。运行时还会注册本地READ结果缓冲区，该缓冲区不向对端发布，因此不计入这五类资源。

### 部署模型

gd_hnsw采用对等部署：**一个进程负责一个数据分片**。

- 每个进程运行相同的程序，加载自己的分片并持有完整的上层图副本与全局元信息。
- 任一进程都可以接纳查询并维护该查询的全部搜索状态；遇到跨分片边时，通过URMA访问邻居所在进程的数据，继续同一次搜索。
- 分片边界只决定数据在哪里，不限制图搜索的范围；一次查询可以访问多个乃至全部分片，但各分片无需分别完成一次本地top-K检索。

### 线程模型

每个进程运行五类线程。

**表 2** 五类线程职责

| 线程 | 主要职责 |
|------|----------|
| Control | 接纳查询、分配Search线程，管理活动查询数量与超时，回收查询资源；固定1个 |
| Search | 推进查询、维护搜索状态，计算本地及拉回向量的距离，生成最终结果 |
| Distance | 处理其他进程的距离计算请求，使用本地向量计算指定ID的距离 |
| READ Progress | 推进远端邻接表与向量的URMA READ，并参与查询阶段的就绪通知 |
| RPC Progress | 发送本进程的距离请求、接收返回结果，并把本进程Distance的计算结果发回请求方 |

线程数量默认按可用CPU（Central Processing Unit，中央处理器）数自动解析（auto），也可显式配置；线程支持CPU绑定、拓扑布局与进度模式配置。查询等待远端操作时，Search线程可以继续处理其他就绪查询。调优方法请参见《[最佳实践](./best_practices.md)》。

## 算法原理

### HNSW算法概述

HNSW是一种基于多层图的近似最近邻搜索算法。

- **多层图结构**：上层稀疏、下层稠密（第0层包含全部节点）。查询从入口点出发，逐层贪心下探到第0层，在第0层做beam search（`ef_search`宽度的候选集维护）。
- **关键参数**
  - `M`：上层每层最大邻居数（默认16）。
  - `M0`：第0层最大邻居数（默认32）。
  - `ef_construction`：建图候选宽度，越大图质量越高、构建越慢。
  - `ef_search`：查询候选宽度，越大召回越高、时延越高。
- **距离度量**：支持L2（L2 Norm，欧氏距离）与IP（Inner Product，内积）两类；运行时可选dot+norm优化路径（仅限L2度量）。

### 全局图索引与分片基线对比

传统分片式检索将数据划分为多个分片，各分片独立建图、独立检索，再由协调节点汇聚重排序。gd_hnsw则先在全部数据上构建一张完整的HNSW图，再将图分片存储，**保留跨分片的图边**。

**表 3** 分片基线方案与gd_hnsw全局图方案对比

| 对比项 | 分片基线方案 | gd_hnsw全局图方案 |
|--------|--------------|-------------------|
| 索引组织 | 先划分数据，各分片独立建立局部图 | 在全部数据上构图，再将图分片存储 |
| 图的连接范围 | 每张局部图只连接本分片内的向量 | 保留不同分片之间的连接，逻辑上仍是一张完整图 |
| 一次查询 | 在各局部图分别搜索，再汇聚结果 | 沿同一张全局图跨分片搜索，生成一份结果 |
| 集群总距离计算量（规模模型） | P·log(N/P) | log N |

以距离计算次数衡量搜索工作量。设数据集包含N个向量，均匀分布在P个分片上。为说明计算量的变化，假设图搜索工作量随数据规模按对数增长。

在该规模模型下，独立分片索引需执行P次局部搜索，总计算量按`P·log(N/P)`增长；全局图只执行一次搜索，计算量按`log N`增长。数据量缩小为1/P，并不意味着一次局部图搜索的计算量也缩小为1/P，因此多次局部搜索可能放大集群总工作量。两种表达式用于比较增长趋势，不表示任意N、P下都存在固定的大小关系。

全局图保留跨分片导航路径，一次搜索可持续向更近区域推进，减少各局部图分别导航的额外开销。

>上述对数关系用于说明计算量放大的原因，不能直接换算为并行查询耗时，实际比较应采用相同的目标召回率。

### 距离下推（pushdown）

远端邻居的距离计算可下发到向量所在进程，由其Distance线程就地计算后回传“ID+距离”。距离下推把“大块向量跨节点搬运”转化为“少量距离结果跨节点回传”，减少原始向量的跨节点传输，并分担查询进程的搜索线程负担。结果集合已满时，下推请求还会携带当前最差结果距离作为上界，远端只回传距离不大于该上界的ID与距离，减少响应数据量。

## 关键特性

- **全局图索引**：在全部数据上构建一张HNSW图再分片存储，保留跨分片边；一次查询沿全局图搜索，直接产出全局top-K，无需各分片独立召回再归并。
- **距离下推**：远端分片向量的距离计算下发到数据所在进程就近执行，配合组内排序与结果上界过滤，降低跨节点传输量。
- **URMA数据面**：远端邻接表/向量经URMA READ单边读取，距离任务经WRITE_NOTIFY投递，配合五块注册内存与资源目录实现零拷贝跨节点访问。
- **多线程并行与查询间重叠**：五类线程分工，通信与计算重叠；查询等待远端操作时Search线程切换处理其他查询。
- **并发资源管理**：查询池限制在途查询；查询级超时与操作级超时保障长尾可控；支持优雅退出（drain）。
- **可观测性**：运行时内置分阶段耗时与队列水线等画像计数，用于定位瓶颈在搜索、通信还是距离服务。
- **Milvus一体化接入**：经C ABI（`ub_c_api.h`）接入Milvus QueryNode，由接入层按开关分流接管裸向量检索请求；接入行为细节请参见Milvus侧资料。
