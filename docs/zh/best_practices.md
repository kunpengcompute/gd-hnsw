# 最佳实践

本文汇总 gd-hnsw 的调优指南：先让召回率达标，再在达标前提下提升吞吐（QPS），最后压缩时延。所有参数均可通过配置文件或命令行设置，生效口径以 `configs/*.env` 与各数据集配置为准。

## 1. 参数总览

| 参数 | 作用域 | 默认 | 影响 |
| --- | --- | --- | --- |
| `ef_search` | 查询 | 索引内默认 | 结果集合容量；召回与 QPS 的主旋钮 |
| `expand_batch` | 查询 | 1 | 每轮展开的节点数；摊薄远端读取开销 |
| 距离策略（`pull` / `pushdown` / `auto`） | 查询 | `auto` | 远端邻居距离的取得方式 |
| `max_active_queries` | 部署 | 配置决定 | 查询池大小，限制并发与内存 |
| Search / Distance / READ Progress / RPC Progress 线程数 | 部署 | auto | 运行时线程配比 |
| `build.M` / `build.ef-construction` / `build.cluster` | 构建 | 配置决定 | 图质量与数据布局（离线，重建生效） |

调优顺序建议：**构建合格索引 → 调 `ef_search` 使召回达标 → 调运行时参数（线程、距离策略、批大小）提升 QPS → 校验时延 < 50 ms**。

## 2. 召回率与吞吐：`ef_search`

`ef_search` 控制本次搜索的结果集合容量，搜索结束时从该集合中选取 top-k：

- 增大 `ef_search`：召回率上升，距离计算量与远端访问量同步上升，QPS 下降；
- 减小 `ef_search`：方向相反。注意 `ef_search` 必须不小于 `k`。

推荐标定方法：

1. 固定其他参数，用 `gd_hnsw_bench` 在一组递增的 `ef_search` 上测量 recall@k 与 QPS；
2. 画出 recall–QPS 曲线，选取**召回达标线上 QPS 最高的点**；
3. 保留少量召回余量，避免数据或环境波动导致不达标。

> 验收要求召回率 > 0.95。若目标数据集几乎无调参余量（召回紧贴达标线），不要再降 `ef_search` 换 QPS，转而从第 3～6 节的运行时方向挖掘吞吐。

## 3. 距离策略：Pull 与 Pushdown

远端邻居的距离有两种取得方式，同一轮内可按分组混合使用：

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `pull` | URMA READ 拉回远端向量，本地计算 | 组内 ID 少、向量维度低、对端负载高 |
| `pushdown` | 下推计算任务到向量所在节点，只回传 ID 与距离 | 组内 ID 多、向量维度高、本端算力紧张 |
| `auto` | 按分片分组内 ID 数量自动选择：小于阈值拉取，否则下推 | 一般场景（默认） |

量级参考（详设估算：10 亿条 1024 维 float32、2 节点均分、单节点 1000 QPS、每查询评价 1 万条向量）：

- 朴素拉取：每查询跨节点传输约 0.02048 GB，有效带宽需求约 20.48 GB/s；
- 全部下推：每查询跨节点传输降至约 64 KB，带宽需求降低两个数量级，同时把一半距离计算分担给对端。

实践要点：

- 高维数据集（gist 960 维 / bge / openai 1536 维）上向量传输占比高，优先确认 `auto` 阈值将大组导向 `pushdown`；
- 下推请求在结果集合已满时自动携带当前最差距离作为上界，远端只回传更优候选，无需手工配置；
- 邻居 ID 在组内默认排序，使同分片访问更集中；排序范围可配置，超大分组可适当收窄以降低排序开销。

## 4. 线程配比

每个进程固定 1 个 Control 线程，其余四类默认 `auto`（设可用逻辑 CPU 数为 `C`）：

| 线程 | auto 数量 | 职责 |
| --- | --- | --- |
| Search | 扣除其余线程与预留后的剩余 | 推进查询、维护搜索状态、本地距离计算 |
| Distance | `max(1, ⌊C/6⌋)` | 处理他节点的距离下推请求 |
| READ Progress | `max(1, min(2, ⌊C/24⌋))` | 推进远端邻接表/向量读取 |
| RPC Progress | `max(1, min(4, ⌊C/12⌋))` | 距离请求收发与结果回送 |

预留 CPU 为 `max(1, ⌊C/12⌋)`（含 Control）。使用 `configs/default.env` 默认启动时，READ Progress 与 RPC Progress 显式为 1，Search 与 Distance 仍为 `auto`。

何时需要显式调整：

- **QPS 上行但时延尾部分位恶化**：Search 过少导致查询排队，或通信线程过少导致就绪通知延迟；先核对各类线程的占用，再针对性增加；
- **Distance 成为瓶颈**（下推请求排队、对端时延上升）：增加 Distance，或检查是否过多大组被导向 `pushdown`；
- **单机多进程（容器）混部**：`C` 按进程可用 CPU 计算，务必用 cgroup/绑核限定各进程份额，避免 auto 推导超额占用；
- 不建议为追求单一指标极限而长期偏离 auto 配比，auto 已按职责成本标定。

## 5. 并发与内存：`max_active_queries`

- 节点预分配固定数量的查询位置（查询池），`max_active_queries` 决定上限；每个位置保存一条查询的输入、参数与执行进度；
- 并发上限 = `max_active_queries`；压测时聚合并发 = `max_active_queries × 进程数`；
- 增大该值提升并发潜力，但线性增加内存占用，且过多在途查询会加剧线程切换与远端等待，时延尾部分位变差；
- 建议从默认配置起步，在召回达标、时延 < 50 ms 约束内逐步上调，观察 QPS 是否仍近似线性增长；不再增长时即为该形态的饱和点。

## 6. 数据布局与构建侧

构建参数离线生效，重建索引才可变更：

- `build.M`：每节点邻居数。增大提升图连通性与召回上限，索引体积与构建时间同步上升；
- `build.ef-construction`：构建期搜索宽度，影响图质量；离线成本，建议充足；
- `build.cluster = true`：k-means 聚类分片，让相近向量落在同分片，提升数据局部性、减少跨分片访问；同时生成 idmap / centroids 伴生文件，查询路由可按最近聚类中心分发；
- `build.shards`：分片数决定部署形态，**必须等于运行时进程数**（每进程加载一个分片，rank 与分片一一对应）。

数据布局直接影响远端访问频率：聚类分片 + 中心路由通常比均匀切分获得更少的跨分片边遍历，从而降低通信占比。

## 7. 基准测量方法

- 使用 `gd_hnsw_bench`，先 warmup 再计时，`rounds` 多轮取统计值，关闭无关负载；
- 报告口径：recall@k（对 ground-truth）、聚合 QPS（各进程求和）、每查询时延分位数（关注 p99 是否 < 50 ms）；
- 变更单个变量再测量：先 `ef_search`，再线程配比，再 `expand_batch` / 距离策略；多变量同时改无法定位收益来源；
- `expand_batch` 从默认 1 起步，增大后一轮可读取多个节点邻接表，能摊薄提交/通知开销，但会拉长单轮等待并增加缓冲占用，需实测权衡。

## 8. 验收 checklist

- [ ] recall@k > 0.95（gist / bge 或目标数据集）
- [ ] 同等算力下 QPS 对比 32 分片独立索引方案提升达标
- [ ] 查询时延 p99 < 50 ms
- [ ] 进程数 = 分片数，各节点 URMA 组网连通
- [ ] 接入 Milvus 时，`queryNode.ub.enabled` 链路异常可安全回退原生检索路径
